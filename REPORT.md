# Issue #44 — Resource safeguards for hostile and malformed files

Branch `feat/safeguard` in clone `/c/Users/Error/projects/ferrix-safeguard`.

## Status

Work in progress — first commit landed with all three gates passing.

## What landed

New `crates/ferrix-io/src/safeguard.rs` plus `safeguard/tests.rs`, and the
importers rewired through it.

### The biggest concrete defect, fixed

`xlsx.rs` and `table_xlsx.rs` had six XML readers matching
`Ok(Event::Eof) | Err(_) => break` (or the `while let Ok(..)` equivalent). A
parse ERROR and a clean end of file were the same thing, so a truncated or
corrupt part imported as a SHORTER, silently-wrong result — a workbook losing
half its defined names, a styles part losing `<cellXfs>` entries and shifting
every later style index. All six now separate the two and propagate
`SafeguardError::MalformedXml` naming the part and the byte offset.

### Safeguards

- **Zip bomb**: `inspect_archive` reads only the central directory (via
  `by_index_raw`, no decompressor built) and refuses on declared/compressed
  ratio > 200x above a 4 MB floor. Nothing is extracted.
- **Entity expansion**: `guard_event` refuses `DocType` and any named entity
  reference that is not one of the five predefined ones — *including entities
  hidden in attribute values*, which produce no `GeneralRef` event and were
  the actual bypass (billion-laughs is written as `<sheet name="&lol4;"/>`).
  quick-xml's non-expansion is pinned by
  `entity_expansion_is_not_possible_in_this_quick_xml`.
- **Bounded memory**: `Limits` derived from `Budget::claim_bytes()`, enforced
  per-part and as a running total by `PartBudget`. Replaces three copies of
  `Vec::with_capacity(entry.size())` — an allocation sized from an
  attacker-controlled field.
- **Cancellation**: `CancelToken` threaded through `import_xlsx_guarded`
  (between sheets, and every 8192 cells) and `scan_part` (every 4096 events).
  A cancelled import returns `Err` and drops every sheet built so far.
- **Path traversal**: `safe_entry_path` refuses `..`, absolute, drive-letter
  and backslash-separated escapes; checked in both `inspect_archive` and
  `read_all_parts`.
- **Formula depth**: `ParseError::TooDeep` at `MAX_PARSE_DEPTH = 256`, counted
  on the `Parser` struct so `parse_expr`/`parse_prefix` share one counter.

### Fuzz / property tests

Deterministic xorshift PRNG with fixed seeds (printed in failure messages).
400 truncations, 400 byte-flip mutations, 200 random-byte documents. Each
asserts no panic AND that any error names the failing part. Lower bounds on
the detection count (`errored > 200`) stop the tests passing against a
scanner that accepts everything.

## WHAT I DID NOT VERIFY

- **No real-world malicious xlsx was ever tested.** Every hostile fixture is
  synthetic and generated by the test itself. This proves the checks fire on
  the shapes I constructed, not that they catch what is in the wild.
- **Excel was never launched.** No claim is made about how Excel treats any
  of these files.
- **calamine's own hostile-input behaviour is bounded, not audited.** I gate
  what is handed to it (archive vetted before `open_workbook`, largest
  declared part checked against the per-part cap), but I did not fuzz
  calamine itself. It remains a second parsing path I do not control.
- **The zip crate's central-directory parse is not bounded by me.**
  `ZipArchive::new` builds an index map of every entry before my code runs;
  `max_entries` rejects afterwards. An archive with a huge entry *count*
  still allocates proportionally inside `zip` first.
- **No memory was measured.** "Bounded" here means the byte accounting in
  `PartBudget` refuses past the cap; I did not profile RSS during an import.
- **The 200x ratio and 256 depth constants are reasoned, not measured**
  against a corpus of real spreadsheets.
